# Approval-gated software factory

Issue #16 tracks the full factory. This PR delivers **read-only planning and trusted GitHub collection controls**, not an activated cloud-agent dispatcher.

Use the scoped issue template to describe scope, acceptance checks, regression tests, file paths and dependencies. The manual Propose approved issue work workflow runs on main with read-only contents/issues/pull-request permissions. Its collector fetches scoped issues, exact owner approval comments, explicit dependency states and open PR file scopes directly from the fixed repository. It handles bounded pagination and rejects incomplete/changing file scopes. No issue body or discussion is copied into the workflow summary. An offline JSON file is only a planning/test input, never evidence of authorization to perform paid or external work.

`node scripts/factory-plan.mjs trusted-snapshot.json` reads that snapshot and prints a proposal. The module exposes `issueScopeDigest(issue)` so a trusted collector can show the owner the exact SHA-256 of repository, issue number, title and body. A matching owner comment `/factory approve DIGEST` is valid for seven days; edits invalidate it. The `agent-ready` label indicates readiness only. The planner never posts approvals or comments itself.

The snapshot contains `repository`, an `issues` array with number/title/body/state/labels/comments (comment author login, body and created_at), and an explicit `active` array with issue/files/state for running work. Missing/ambiguous scopes fail closed. Readiness parsing accepts CRLF while approval hashes retain the exact original body. Every required section must occur exactly once, including Markdown forms with up to three leading spaces or optional closing hashes. Dot/root segments, repeated separators and noncanonical active-run paths are rejected; a trailing directory slash is canonicalized before protection/conflict checks. Closed or missing dependencies are distinguished; only closed dependencies satisfy the gate. The collector re-reads candidate scope after comments and verifies PR head/file-count stability after reading files. Renamed paths keep both old and new paths locked. Review PRs keep scope/issue locks but do not consume a coding slot; draft bot PRs conservatively count as running. Empty or very large PRs stop collection for human review.

At most two independent candidates fit alongside active work. Overlapping file/directory scopes serialize. Authorization, credential vault, operational telemetry and owner-bound provider/action/reminder/push/private-record/quota modules, deployment, migrations and factory configuration are protected and require separate human handling. One branch/PR per issue prevents batching unrelated code changes into a single unreviewable change.

## GitHub cloud-agent task reads (issue #40)

`createGitHubTaskReader` in `scripts/factory-github-tasks.mjs` implements the fixed-repository task-list and task-detail GET interfaces. A trusted host supplies its scoped user credential; the module has no CLI, workflow trigger, start, cancellation or credential-discovery path. It is not connected to the simulation controller or the production Worker. Never place a personal CLI credential in the coding sandbox or public workflow.

The reader checks both archived and non-archived task inventories with bounded pagination, per-response size and time limits, no redirects/retries, and exact task/repository identity checks. All advertised pagination relations must agree with the requested bucket and page progression; a later last page without a next link blocks readiness. When a response advertises `total_active_count` and `total_archived_count`, both must be nonnegative integers, remain present and stable through collection, and exactly match their respective collected buckets. The current API examples omit these totals, so absence is supported; absent totals cannot prove that an upstream service omitted no rows. Duplicate rows, malformed pagination, denied requests, unknown states and contradictory terminal sessions make readiness unknown rather than implying idle capacity. Output contains only task/session IDs, validated states and terminal flags; prompts, diagnostics and credentials are omitted. Every result retains `dispatchEnabled: false`; inspection also retains `cancellationAvailable: false`.

These reads are point-in-time observations, not atomic dispatch locks, authenticated owner approvals, budget evidence or proof of write access. Concurrent task changes can invalidate the observation; a future live controller must recheck state under its durable claim. Session detail must be complete and consistent before accepting a terminal result. A failed/oversized read blocks readiness rather than providing a partial inventory.

The [task API reference](https://docs.github.com/en/rest/agent-tasks/agent-tasks) documents user-token authentication and Agent tasks permissions. The [Actions cancellation API](https://docs.github.com/en/rest/actions/workflow-runs#cancel-a-workflow-run) requires Actions: write, but task-to-run correlation and its effect on a live agent remain unverified. Do not infer ownership from matching timestamps or branch names, and do not call Actions cancellation merely because a historical run is cancelled. Current synthetic regression tests verify read semantics and failure handling only; no live adapter acceptance or factory activation is claimed.

## Running a read-only proposal (existing collector)

After this PR is reviewed and merged, open Actions → Propose approved issue work → Run workflow on main. It uses the shared Node pin and no npm install or model dependency. The GitHub-provided token has read-only repository scopes, exists only in the collection step, is never printed or persisted, and can only be sent to the fixed GitHub API origin with redirects disabled. There are no issue/label/comment writes, agent assignments, PR creation, merges, migrations or deployments.

The output lists issue numbers, scope digests, static blocked reasons and candidate file scopes only. It is a proposal, not authority to execute. Incomplete pagination, more than the request cap, a redirect, missing permission, an empty/overlarge PR, or a changing head causes the run to fail without producing a complete plan. No live workflow run has been triggered by this PR. Approval must be rechecked at future dispatch time; snapshot collection cannot make a cross-request GitHub snapshot perfectly atomic.
