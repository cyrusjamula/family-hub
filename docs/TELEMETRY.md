# Restricted error diagnostics

Issue #14 tracks the full observability work. The implementation adds server-generated correlation IDs, restricted error records, an owner-only lookup, scheduled-job failure references, opt-in coarse browser-error events, and optional feedback references. It does not enable collection or publish incidents automatically.

Each Worker response gets `x-request-id`, generated by the server and never copied from a client header. JSON error objects include the same `requestId` and append it to the safe error message (or a safe fallback if no error string exists), preserving other result fields, so the existing UI can show a reference without copying any extra page content. Success responses preserve their payloads. An exception inside instrumentation never triggers a second provider attempt.

## Data stored

When enabled, authenticated errors store only these fixed fields: generated reference ID, UTC epoch timestamp, allowlisted route name (or `/other`), allowlisted HTTP method, status, bounded duration, a fixed error category, and a validated release SHA (or `unknown`). Scheduled failures use a fixed job name and a safe failure reference. No identities, email addresses, IP addresses, browser fingerprints, cookies, tokens, headers, query strings, raw paths, request/response content, exception messages, stacks, conversations, private records, screenshots or locations are stored.

This intentionally provides coarse diagnosis. It cannot reconstruct a prompt, source document, provider error body or arbitrary stack trace. Browser reporting is off per device until a member opts in under Settings; an enabled browser sends only a fixed event category and fixed app-section name, with no error message, stack, URL, DOM, form value, screenshot, clipboard, keystroke, user-agent, device fingerprint or location. At most five events are attempted per page load. Offline errors and reporting failures are ignored and never mask the original browser error. The server kill switch and storage caps still apply.

The browser endpoint accepts only the `exception`/`rejection` event types and `chat`/`planner`/`settings`/`advanced` sections, with a 512-byte request-body limit. Its restricted record uses `method=BROWSER`, `status=0` (not an HTTP response), and a fixed `browser/<section>` route. It assigns the reference and release on the server; client-provided extra fields are ignored. A displayed browser reference can be copied into the optional related-reference field on a private feedback report. Feedback stores that UUID and the validated release inside its existing encrypted payload. The release and UUID appear in the exact GitHub issue preview only after owner review; they identify a restricted diagnostic but include no diagnostic contents.

## Limits and failure behavior

- Collection defaults off. Set runtime `TELEMETRY_ENABLED=true` only after review and the additive migration.
- No successful request sampling or unauthenticated request logging. Diagnostic lookups are not persisted, preventing self-amplifying logs. The normal platform request metrics remain separate.
- At most 200 persisted errors per UTC day, at most 1,000 rows total, and seven-day retention. The insertion cap is checked atomically in D1. Old rows are removed on a later stored-error attempt; lookup excludes expired rows even before physical cleanup. This is not a scheduled deletion guarantee.
- HTTP storage is best effort via `waitUntil`; missing execution context or failed storage never changes an operation's status or causes it to retry. A reference may therefore have no retained row. Scheduled jobs remain failed on errors and expose only a safe reference.
- No provider, model, paid log service, log export or new storage service is invoked. Existing D1/Workers platform usage still applies; confirm the account's limits before enabling. No paid subscription or extra usage is authorized by this code.

## Owner investigation

The owner signs into the Hub and reads `/api/diagnostics?id=REQUEST_REFERENCE`. The server verifies the authenticated owner before touching diagnostics storage. Other family roles cannot inspect logs, even with a valid reference. Invalid IDs are rejected and queries are bound parameters. Nothing automatically goes to a public GitHub issue. The owner must review any sanitized diagnostic summary before sharing it.

## Rollout (not performed)

1. Review/apply migration `0008_diagnostics.sql` to the existing restricted D1 database. This number reserves 0007 for the independent feedback PR; neither feature depends on the other's schema. Do not run unrelated pending migrations implicitly.
2. Deploy the reviewed code through the normal validation gate.
3. The build records its validated source commit using Cloudflare `WORKERS_CI_COMMIT_SHA`, GitHub `GITHUB_SHA`, or the checked-out Git commit. A build SHA takes precedence over a stale runtime override; `TELEMETRY_RELEASE` is only a development/unbundled fallback. Opt into `TELEMETRY_ENABLED=true`. This does not provision a credential or change sharing. Invalid release values become `unknown` rather than being logged.
4. Generate one authorized, harmless validation error, confirm its UI/header reference and owner lookup, verify denial from another role, and test the kill switch. Opt a synthetic browser session in and verify the browser-event reference and owner lookup. No such live test has been performed by this PR.

Owner lookup also groups retained records by fixed route, method, status, category and release, returning occurrence count and first/last timestamps. It makes no provider calls or automatic GitHub issues, adds no identity fields, and never groups different releases or error categories. A grouping failure leaves the individual reference readable.

Raw telemetry must never be attached automatically to public issues.
